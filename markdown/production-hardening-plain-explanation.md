# Blog Cloud 生产加固通俗说明

可以把这个项目想成一家网上店铺：

- HTTPS 是给店门装上加密门锁，别人不能偷看顾客和店铺说了什么。
- Cookie Secure/SameSite 是把登录小票放好，不让它随便跑到别的网站手里。
- CSRF 是防止坏网页冒充顾客按按钮，比如偷偷点赞、发评论、改资料。
- Gateway 请求防护是在店门口先看一眼，太奇怪、太长、明显危险的请求先挡住。
- 接口级权限是确认“这个人有没有资格做这件事”，不是只看他有没有进门。
- 上传文件校验是防止别人把危险文件伪装成头像塞进系统。
- 后面的 Actuator、密钥、容器限制、告警、备份、ES 重建、MQ 死信、压测、CDN、负载均衡、分布式，是让这家店真的能长期营业、出事能救、流量大也不垮。

## 已完成的阶段 1 到阶段 6

### 阶段 1：HTTPS 和反向代理

我改了什么：

- 加了 HTTPS 反向代理的配置模板。
- 让 Gateway 能识别前面代理传来的真实协议、域名和用户 IP。
- 本地没有真实证书时，不强行让 443 容器失败。

为什么要这样改：

如果用户登录、发评论、改资料时还走明文 HTTP，就像在大街上大声报银行卡密码。HTTPS 的作用就是把浏览器和服务器之间的话加密。

改完有什么好处：

- 生产环境可以放到 HTTPS 后面。
- Cookie 的 Secure 策略有地方生效。
- 以后接 CDN、负载均衡、WAF 时，Gateway 能知道用户原来是用 HTTPS 进来的。

### 阶段 2：Cookie Secure、HttpOnly、SameSite

我改了什么：

- 登录 token cookie 加了 `HttpOnly`，普通 JS 不能随便读。
- 生产默认 `Secure=true`，只在 HTTPS 下发送。
- 默认 `SameSite=Lax`，减少跨站带 cookie 的风险。
- 本地开发可以通过配置关闭 `Secure`，否则本地 HTTP 会登录不了。

为什么要这样改：

Cookie 就像登录小票。以前如果放得太随便，别的网站或者脚本就可能拿它办坏事。`HttpOnly` 是不让前端脚本偷看，`Secure` 是只走加密路，`SameSite` 是不让它随便跟着别的网站请求跑出去。

改完有什么好处：

- 登录态更安全。
- 生产和本地开发都能兼顾。
- 为后面的 CSRF 防护打基础。

### 阶段 3：CSRF 防护

我改了什么：

- Gateway 加了 `CsrfProtectionFilter`。
- 登录后服务端会发一个 `BLOG_CSRF_TOKEN`。
- 前端对 `POST/PUT/PATCH/DELETE` 这类会改数据的请求，自动把这个 token 放到 `X-CSRF-Token` 请求头里。
- Bearer token 形式的 API 客户端不被这个规则误拦。

为什么要这样改：

浏览器会自动带 cookie。坏网页可以诱导用户浏览器去点“发评论”“点赞”“退出登录”，如果后端只看 cookie，就分不清是真用户自己点的，还是坏网页借他的浏览器偷偷点的。

CSRF token 的意思是：你光有登录小票还不够，改数据时还要拿出一个只有本站页面能读到的小口令。

改完有什么好处：

- 坏网页更难冒充用户执行写操作。
- 点赞、收藏、评论、退出登录这类按钮有了额外校验。

### 阶段 4：Gateway WAF-like 请求防护

我改了什么：

- 增加了 `RequestGuardFilter`。
- 增加了 `SecurityGuardProperties` 配置。
- 现在 Gateway 会提前拦截这些请求：
  - 请求体声明太大。
  - query 太长。
  - 单个 header 太长。
  - URL 里有明显路径穿越，比如想访问 `../secret`。
  - URL 或参数里有控制字符。
- 被拦截时返回统一 JSON。

为什么要这样改：

Gateway 就像店门口。明显拿着异常包裹、绕后门、写一大串奇怪地址的人，没必要放进店里再问每个柜台。先在门口挡掉，可以减少后面服务的压力和风险。

但这个不是完整 WAF。真正生产还应该接云 WAF，比如防 SQL 注入、XSS、恶意扫描、机器人流量、CC 攻击等。

### 阶段 5：接口级权限校验

我改了什么：

- 用户服务里一些管理接口加了 `@AdminOnly`。
- 用户管理操作在 service 层也检查是不是管理员。
- 文章编辑、删除、管理改成作者或管理员才能做。
- 评论删除改成评论作者或管理员才能做。
- 不再只靠 Gateway 判断“有没有登录”，业务服务自己也判断“有没有资格”。

为什么要这样改：

登录只代表“你是谁”，不代表“你什么都能做”。比如进了小区，不代表可以进别人家；进了公司，不代表可以看财务后台。

企业项目里，权限一定要落到接口和业务层。否则攻击者只要猜到一个接口地址，就可能越权改别人的文章、删别人的评论、查看管理信息。

### 阶段 6：上传文件校验

我改了什么：

- 新增 `AvatarStorageService` 管头像上传。
- 头像访问时，只允许访问系统生成格式的文件名。
- 返回给前端的是 `/api/user/avatar/{filename}`，不暴露服务器真实磁盘路径。

改完有什么好处：

- 伪装文件更难上传成功。
- 避免用用户提供的文件名造成路径问题。
- 不把服务器目录结构暴露给外面。
- 后续迁移到 OSS、对象存储也更容易。

### 阶段 8：默认密钥轮换

开发环境默认密码可以方便本地跑，但生产如果还用默认 JWT secret、数据库密码、RabbitMQ 密码，就像店铺开业还用出厂默认门锁。

应该怎么做：

- 每个环境单独生成密钥。
- 密钥不进代码仓库。
- 支持定期轮换。
- 轮换前后有兼容期和回滚方案。

### 阶段 9：容器资源限制

容器也要有饭量限制。

为什么要管：

一个服务如果内存暴涨，可能拖垮整台机器。Elasticsearch、Nacos、RabbitMQ、Java 服务都要有 CPU 和内存边界。

应该怎么做：

- Docker Compose 或 Kubernetes 都配置 CPU、内存。
- JVM 参数和容器内存匹配。

### 阶段 10：告警规则

监控不是只看图，关键是出事能叫醒人。

为什么要管：

用户已经打不开页面时，团队才知道出事，那就晚了。

应该怎么做：

- 服务 down 告警。
- 错误率升高告警。
- p95 延迟升高告警。
- JVM 内存高告警。
- RabbitMQ 队列堆积告警。
- ES、MySQL、Redis、Nacos 健康异常告警。

### 阶段 11：备份和恢复

备份不是为了好看，是为了能救命。

为什么要管：

数据库删错、服务器坏了、ES 索引丢了、配置被改坏了，如果没有恢复流程，就会从技术事故变成业务事故。

### 阶段 13：MQ DLQ 运维面板

死信队列像“处理失败的包裹暂存区”。

为什么要管：

通知消息、互动消息如果消费失败，不能直接丢，也不能无限重试拖垮系统。要进 DLQ，运维能看数量、看原因、少量重投。

- 单次重投有限制。
- 记录谁在什么时候重投了什么。
- 防止一键重投造成雪崩。

### 阶段 14：压测基线

压测是提前知道这家店最多能接待多少人。

为什么要管：

不压测就上线，等真实用户来了才知道扛不住，会非常被动。

应该怎么做：

- smoke 测试确认基本链路没坏。
- baseline 测试记录吞吐、错误率、p95 延迟。
- 每次大改后对比基线。

### 阶段 15：动态封禁和可信代理 IP

真实线上一般会经过 CDN、WAF、负载均衡。应用看到的 IP 可能不是用户真实 IP。如果随便相信 `X-Forwarded-For`，攻击者可以伪造 IP。

应该怎么做：

- 只信任来自可信代理的 `X-Forwarded-For`。
- Gateway 用 Redis TTL 做动态封禁。
- 和限流、WAF 告警联动。
- 黑名单是辅助，不是核心安全策略。

### 阶段 16：CDN、负载均衡、分布式部署

这是从“单机本地项目”变成“真正线上系统”的路。

为什么要管：

一台机器坏了不能全站挂，一台服务忙了不能全站卡，图片和静态资源不该都压到后端。

应该怎么做：

- CDN 放静态资源、公开头像、公开图片。
- API 只缓存公开 GET，不能乱缓存带登录态的响应。
- 负载均衡放在 Gateway 前面。
- Gateway 和业务服务多副本。
- MySQL、Redis、RabbitMQ、Nacos、ES 都换成高可用形态。
- 头像从本地磁盘迁移到 OSS 或对象存储。

## 如果这是企业级盈利软件，还要考虑什么

### 1. 钱和交易

如果软件要赚钱，就要考虑订单、支付、退款、发票、对账、风控、优惠券、防刷、财务审计。

技术上要做：

- 支付回调验签。
- 订单状态机。
- 幂等处理，防止重复扣款。
- 对账任务。
- 退款和补偿流程。

### 2. 用户和权限

盈利软件里，用户不只是普通用户，还可能有管理员、客服、运营、审核员、商家、代理商。

技术上要做：

- RBAC 或 ABAC 权限模型。
- 后台操作审计日志。
- 敏感操作二次确认。
- 管理员最小权限。

### 3. 安全合规

真实用户数据不能随便存、随便看、随便导出。

技术上要做：

- 密码强度和加密存储。
- 敏感字段脱敏。
- 数据传输 HTTPS。
- 数据库访问审计。
- 漏洞扫描和依赖扫描。
- 安全应急预案。

### 4. 可用性

盈利软件停一分钟可能就损失钱。

技术上要做：

- 多副本部署。
- 自动健康检查和故障摘除。
- 灰度发布和快速回滚。
- 限流、熔断、降级。
- 备份恢复演练。

### 5. 可观测性

出问题时要能回答三个问题：哪里坏了、影响谁、怎么恢复。

技术上要做：

- 指标：QPS、错误率、延迟、资源使用。
- 日志：结构化日志，带 traceId。
- 链路追踪：看请求经过了哪些服务。
- 告警：只叫醒真正需要人处理的问题。

### 6. 性能和容量

不能靠感觉说“应该能扛住”。

技术上要做：

- 压测基线。
- 容量评估。
- 数据库索引检查。
- 缓存策略。
- 热点接口隔离。

### 7. 数据治理

数据是企业资产。

技术上要做：

- 数据备份。
- 数据恢复演练。
- 数据生命周期。
- 数据归档。
- 删除和导出合规。

### 8. 研发流程

不是写完代码就上线。

技术上要做：

- 代码评审。
- 单元测试、集成测试、端到端测试。
- CI/CD。
- 自动化部署。
- 变更审批。
- 发布记录和回滚计划。

## 成熟公司通常怎么落地

这里不是说腾讯、阿里、字节、百度内部一定逐条完全一样，而是说成熟互联网公司常见的落地方式。

### 1. 平台化

他们不会让每个业务团队都从零搭 WAF、监控、日志、发布系统。

常见做法：

- 统一网关。
- 统一登录和权限中心。
- 统一配置中心。
- 统一日志平台。
- 统一监控告警平台。
- 统一发布平台。
- 统一安全扫描和代码规范。

这样业务团队主要写业务，公共能力由平台团队维护。

### 2. 分层防护

他们不会只靠一个 IP 黑名单。

常见链路：

用户 -> CDN -> WAF -> 负载均衡 -> Gateway -> 业务服务 -> 缓存/数据库/MQ/搜索

每层做自己的事：

- CDN 减少静态资源压力。
- WAF 挡常见攻击。
- 负载均衡分流量、摘除坏实例。
- Gateway 做认证、限流、路由、动态封禁。
- 服务层做权限和业务校验。
- 数据层做备份、高可用和审计。

### 3. 所有东西都可观测

成熟团队不会只说“服务挂了”。他们会看：

- 哪个接口慢。
- 哪个用户群受影响。
- 哪个服务错误率升高。
- 哪个队列堆积。
- 哪个数据库 SQL 慢。
- 哪次发布开始出问题。

### 4. 发布有灰度

他们不会一次把新版本推给所有用户。

常见做法：

- 先发测试环境。
- 再发预发环境。
- 再给 1% 用户。
- 没问题再 10%、50%、100%。
- 出问题马上回滚。

### 5. 故障有预案

成熟公司默认系统一定会出问题，所以提前准备。

常见做法：

- 值班表。
- 故障等级。
- 应急联系人。
- 回滚脚本。
- 数据恢复手册。
- 故障复盘。

### 6. 安全左移

安全不是上线前最后扫一下。

常见做法：

- 写需求时做安全评审。
- 写代码时遵守规范。
- 提交时做依赖漏洞扫描。
- 合并前做代码评审。
- 上线前做安全测试。
- 线上接 WAF、风控和审计。

## 一个完整项目应该长什么样

一个更完整的企业级项目，至少应该有这些层：

### 用户入口层

- 域名。
- HTTPS 证书。
- CDN。
- WAF。
- 负载均衡。

### 接入层

- Gateway。
- 认证。
- 限流。
- CSRF。
- 动态封禁。
- 可信代理 IP 解析。
- 请求日志。

### 业务服务层

- 用户服务。
- 文章服务。
- 评论服务。
- 通知服务。
- 管理后台服务。
- 每个服务都有权限校验和单元测试。

### 数据和中间件层

- MySQL 高可用。
- Redis 高可用。
- RabbitMQ 高可用。
- Nacos 高可用。
- Elasticsearch 高可用。
- OSS 或对象存储。

### 运维层

- Prometheus。
- Grafana。
- 日志平台。
- 链路追踪。
- 告警。
- 备份。
- 恢复。
- 压测。

### 研发交付层

- Git 分支规范。
- Code Review。
- CI 测试。
- 镜像构建。
- 灰度发布。
- 回滚。
- 变更记录。

### 安全治理层

- 密钥管理。
- 漏洞扫描。
- 依赖扫描。
- 权限审计。
- 管理员操作日志。
- 数据脱敏。
- 应急响应。
